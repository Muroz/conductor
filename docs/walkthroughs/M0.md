# M0 — One-command reproducible cluster

Read this before the implementation session. It describes the diff you are going to review.

---

## What you'll have when this is done

A single command, `make up`, that turns an empty machine into a working local Kubernetes
cluster with a way to get HTTP traffic in and a way to get your own container images in.
`make down` removes it. Running `down` then `up` again gives you the same cluster, every time,
with no manual steps in between.

Nothing about Conductor the application exists yet. This milestone builds the ground you will
stand on for the next fourteen.

| File | What it's for |
|---|---|
| `kind/cluster.yaml` | The cluster definition: how many nodes, and which host ports reach into them. Read once by `kind create cluster`. |
| `scripts/registry.sh` | Starts a small container image registry on your machine and teaches the cluster's nodes to pull from it. |
| `k8s/ingress-nginx/deploy-v1.15.1.yaml` | A copy of the ingress-nginx controller manifest, pinned to one version, with one local change we make ourselves. This is the thing that accepts HTTP on port 80 and routes it into the cluster. |
| `k8s/ingress-nginx/README.md` | Where that file came from, the exact command that produced it, and what we changed. So the next person can re-vendor it without guessing. |
| `Makefile` | `up`, `down`, `reset`, `load`. The only interface you use. |

`Makefile` and `kind/cluster.yaml` started as hand-written drafts that created a cluster and
stopped there. The implementation session replaced both.

### Words you need for the table above

- **Node** — a machine Kubernetes schedules work onto. With kind, each node is a Docker
  container on your laptop.
- **Manifest** — a YAML file describing a Kubernetes object you want to exist.
- **Ingress controller** — a pod that receives HTTP traffic from outside the cluster and
  forwards it to the right application inside.
- **Registry** — a server that stores container images. Docker Hub is one. We run a tiny
  private one locally.

Every term is also in `docs/lexicon.md`.

## What's not in this milestone

| Not here | Where it arrives |
|---|---|
| Any application code — no FastAPI, no worker, no Postgres | M1 |
| A `Dockerfile`, or anything to actually push to the local registry | M1 |
| Alembic, migrations, a database schema | M1 |
| Deployments, Services, Secrets, ConfigMaps for Conductor | M2 |
| An `Ingress` object for our own app (we install the *controller*, not any rules) | M2 |
| ArgoCD, Kustomize, overlays | M4 |
| Prometheus, Grafana, any metric | M7 |
| TLS / real certificates on ingress | never in this plan; HTTP only |

`make load` is created in this milestone but does nothing useful until M1 exists to be built.
It is here because the image-loading question belongs to M0's syllabus, not because M1 needs
it early.

## The order of work

### 1. `kind/cluster.yaml` — define the cluster

**What it is.** The YAML that says: one control-plane node, two worker nodes, host ports 80
and 443 wired into the control-plane node, and a pinned Kubernetes version.

**The version pin.** Every node sets
`image: kindest/node:v1.35.5@sha256:ce977ae6d65918d0b58a5f8b5e940429c2ce42fa3a5619ec2bbc60b949c0ac95`.
That is deliberately one minor release behind kind v0.32.0's default of v1.36.1, for two
reasons. First, without an `image:` field the Kubernetes version changes silently whenever
kind is upgraded, and this is the reproducibility milestone. Second, the `kubectl` on this
machine is v1.34.1 — Docker Desktop installs one in `/usr/local/bin`, which wins the PATH over
Homebrew's — and Kubernetes supports a client/server skew of one minor version either way.
v1.34 against a v1.36 server is two ahead and unsupported. The digest rather than the plain
tag is what kind's release notes ask for: a tag can be moved, a digest is the content.

**Why it comes here.** Everything else needs a cluster to exist. This file is also read
*only* at creation time — you cannot change the node count or port mappings of a running
cluster. Getting it right first avoids rebuilding three times.

**Where the reasoning is.** `docs/concepts/M0-kind-cluster-anatomy.md#the-config-file-is-read-once`
and `docs/concepts/M0-kind-cluster-anatomy.md#port-mappings-getting-traffic-into-a-node`.

**The reference.**
```
https://kind.sigs.k8s.io/docs/user/configuration/ — the full set of fields: name, nodes/roles,
extraPortMappings (containerPort, hostPort, listenAddress, protocol), kubeadmConfigPatches for
node labels.
pinned: kind v0.32.0  ·  checked: 2026-08-11
```

### 2. `scripts/registry.sh` — the local image registry

**What it is.** A shell script that starts a `registry:3` container named `kind-registry`,
publishes it on `127.0.0.1:5001`, joins it to the `kind` Docker network, writes a containerd
config file on every node pointing `localhost:5001` at it, and applies the conventional
`local-registry-hosting` ConfigMap.

**Why it comes here.** It runs against a live cluster (steps 3 and 5 need `kind get nodes` and
`kubectl`), so it comes after the cluster config. It comes before the Makefile because the
Makefile calls it.

**Where the reasoning is.** `docs/concepts/M0-images-into-the-cluster.md#the-local-registry-and-why-the-alias-is-needed`.

**The reference.**
```
https://kind.sigs.k8s.io/docs/user/local-registry/ — the upstream kind-with-registry.sh script
our version is derived from: registry:3, port 5001, /etc/containerd/certs.d/localhost:5001/hosts.toml,
docker network connect kind, and the KEP-1755 ConfigMap.
pinned: kind v0.32.0  ·  checked: 2026-08-11
```

One deliberate difference from that script: it patches containerd's `config_path` through
`containerdConfigPatches` in the cluster config. The script's own comment says that patch *"is
not necessary with images from kind v0.27.0+"*. The node image we pin is one published by kind
v0.32.0, so we omit the patch, with a comment in `kind/cluster.yaml` saying why. If the
registry turns out not to work, that omission is the first thing to put back.

### 3. `k8s/ingress-nginx/deploy-v1.15.1.yaml` — the ingress controller

**What it is.** A manifest downloaded once from the ingress-nginx repository at tag
`controller-v1.15.1` — 679 lines, 19 objects — committed to this repo with exactly one local
edit: a `nodeSelector` that pins the controller pod to the node that has the port mappings.
The file in the repo is 696 lines, the extra 17 being a provenance header. `k8s/ingress-nginx/README.md`
records the upstream sha256 so drift is detectable.

**Why it comes here.** It needs a running cluster to be applied, and it needs to know which
node carries ports 80/443 — which task 1 decided. It comes before the Makefile because
`make up` applies it.

**Where the reasoning is.** `docs/concepts/M0-ingress.md#why-kind-needs-help-getting-traffic-in`
and `docs/concepts/M0-ingress.md#the-controller-has-to-land-on-the-right-node`.

**The reference.**
```
https://github.com/kubernetes/ingress-nginx/blob/controller-v1.15.1/deploy/static/provider/kind/deploy.yaml
— the exact file we vendor. Controller image registry.k8s.io/ingress-nginx/controller:v1.15.1
pinned by digest; controller container ports 80/443 use hostPort; IngressClass named "nginx";
controller arg --watch-ingress-without-class=true.
pinned: controller-v1.15.1 (released 2026-03-19)  ·  checked: 2026-08-11
```
```
https://kubernetes.github.io/ingress-nginx/deploy/ — source of the readiness wait command:
kubectl wait --namespace ingress-nginx --for=condition=ready pod
  --selector=app.kubernetes.io/component=controller --timeout=120s
Note: this page has no "kind" section any more. The kind manifest still exists in the repo,
which is why the reference above points at a file and not a docs page.
checked: 2026-08-11
```

**Upstream now recommends something different.** kind's ingress page no longer describes
installing a third-party ingress controller at all. It says: *"Since cloud-provider-kind
v0.9.0, it natively supports Ingress. No third-party ingress controllers are required by
default."* We do not use `cloud-provider-kind`, because it is a process you run on your host,
outside the cluster, and keep running — and its README says *"On macOS and WSL2 you must run
cloud-provider-kind using `sudo`"*. `make up` cannot own a foreground `sudo` process, and
"one command, under three minutes, no manual steps" is the entire point of M0. Full reasoning
and both links: `docs/concepts/M0-ingress.md#where-we-diverge-from-what-kind-now-recommends`.

### 4. `Makefile` — wire it together

**What it is.** Four targets.

| Target | What it does |
|---|---|
| `up` | create the cluster from `kind/cluster.yaml` → run `scripts/registry.sh` → apply the vendored ingress manifest → three waits (below) → print the active kubectl context |
| `down` | delete the cluster. Leaves the registry container running. |
| `reset` | `down`, plus remove the registry container and its stored images |
| `load` | `make load IMG=name:tag` — copy a locally built image into every node. Nothing to load until M1 builds one. |

**Why it comes here.** It is the orchestration layer. It can only be written once the three
things it orchestrates exist.

**Why `up` ends with three waits.** The ingress manifest includes a validating admission
webhook — a hook that inspects `Ingress` objects you submit and rejects malformed ones. Its
TLS certificate is generated by Jobs that run after apply. If `make up` returns before those
finish, your first `kubectl apply` of an Ingress fails with a webhook connection error and
looks like your YAML is wrong. Each wait covers a gap the next one doesn't:

1. `kubectl -n ingress-nginx rollout status deploy/ingress-nginx-controller` — not
   `kubectl wait pod`, because the Deployment exists the instant apply returns but its pods
   may not, and `kubectl wait` on a selector matching nothing fails outright with "no matching
   resources found" rather than waiting.
2. `kubectl wait --for=jsonpath='{.webhooks[0].clientConfig.caBundle}'
   validatingwebhookconfiguration/ingress-nginx-admission` — `-create` makes the certificate,
   `-patch` writes the CA bundle into the webhook configuration, and until it has, applying
   any Ingress fails with an x509 error. Controller readiness does not imply `-patch`
   finished. You cannot wait on the Jobs themselves: both carry `ttlSecondsAfterFinished: 0`,
   so they are deleted the moment they complete, and `kubectl wait job/...` fails with
   NotFound. Waiting for the field `-patch` produces is the version that isn't a race.
3. The readiness check from ingress-nginx's own install docs, kept verbatim so you recognise
   it when you read that page.

Together they make `make up` mean "ready", not "submitted".

**Where the reasoning is.** `docs/concepts/M0-kubectl-context.md#why-this-matters-more-than-it-sounds`
covers why `up` also prints the active context.

**The reference.**
```
https://kind.sigs.k8s.io/docs/user/quick-start/ — create-with-config, kind get clusters,
kind load docker-image, and the context naming rule (kind-<cluster-name>); kubeconfig defaults
to ${HOME}/.kube/config when $KUBECONFIG is unset.
pinned: kind v0.32.0  ·  checked: 2026-08-11
```

## The decisions worth arguing with

Three `TODO(learn):` markers go in. Each is a real fork with a defensible other side.

### 1. Three nodes, and we re-add a label upstream deleted

**What I'll do.** One control-plane node plus two workers. Host ports 80/443 map into the
control-plane node only. The control-plane node gets the label `ingress-ready=true`, and the
vendored ingress manifest gets `nodeSelector: ingress-ready: "true"` added by hand.

**Why the hand edit exists.** The upstream kind manifest used to carry exactly that
nodeSelector. It doesn't any more — `ingress-ready` appears in
`deploy/static/provider/kind/deploy.yaml` at tag `controller-v1.12.0` and is gone by
`controller-v1.13.9`. Today the pod selects only `kubernetes.io/os: linux` and tolerates the
control-plane taint. On a **single-node** cluster that is fine: there is one node, it wins. On
**our** cluster the scheduler may put the controller on a worker node — a node with no host
port mapping — and then `curl localhost` gets connection refused while every pod reads
`Running`. Nothing reports an error, because nothing is wrong from Kubernetes' point of view.

**The honest alternative.** Use a single-node cluster and vendor the manifest unmodified.
That is simpler, `make up` is faster, and it stays closer to upstream. The cost: you never see
a pod land on the wrong node, `nodeSelector` stays an abstraction, and `kind load` copying to
three nodes — something you will feel in M1 — never shows up. `plan.md` lists multi-node in
M0's syllabus, which is why I'm taking the more expensive side. If you'd rather have the speed,
say so at review and it's a small change.

**The risk you should hold me to.** Three nodes is slower to create than one. The gate is three
minutes. If it doesn't make it, this decision is the first thing to reverse.

### 2. `make down` leaves the registry container running

**What I'll do.** `down` deletes the cluster only. The `kind-registry` container keeps running
with `--restart=always`, holding every image you have pushed. `reset` is the one that removes
it.

**Why.** The registry is the layer cache. If `down` removed it, every `up` would need a fresh
`docker push` of the whole application image before anything could start — and from M1 onward
you will run `down`/`up` often.

**The honest alternative.** "Down means nothing is left." It is a cleaner promise, and a
lingering container is exactly the kind of hidden state that makes a setup irreproducible on
someone else's machine. The counter-argument is that `make reset` exists to make the strong
promise, and `up` recreates the registry from scratch if it isn't there — so the state is
hidden but not load-bearing. Push on this if you disagree; it's a judgement call.

### 3. Host ports 80/443, bound to 127.0.0.1

**What I'll do.** `containerPort: 80 → hostPort: 80` and `443 → 443`, both with
`listenAddress: "127.0.0.1"`.

**Why.** Port 80 means the gate is `curl http://localhost/foo` with no port number, which is
what you want when you are checking whether ingress works and not whether you typed the port
right. `listenAddress` defaults to `0.0.0.0` — every interface — which puts your dev cluster on
whatever café wifi you are joined to. `127.0.0.1` is the safer default and costs nothing.

**The honest alternative.** Ports 8080/8443. Port 80 collides with anything else on your
machine that wants it, and the symptom is `make up` failing partway through cluster creation
with a Docker bind error, leaving a half-created cluster to clean up. If you already run
something on 80, take 8080 — the only cost is typing the port in every URL for the rest of the
project.

## How you'll know it worked

`plan.md`'s gate for M0:

> `make down && make up` gets you from nothing to a working cluster with ingress in under
> 3 minutes, and you've done it at least twice without editing anything by hand.

**You run every command below. I do not run any of them, at any point, for any reason —
including to check my own work.** These are the exam. If I've built it wrong, the failure has
to be yours to find.

In plain English, four things have to be true.

**1. It comes up from nothing, twice, inside three minutes.**

```sh
make reset                # full clean: no cluster, no registry
time make up
time (make down && make up)
```
Passing looks like: both `real` times under `3m0.000s`, and no step where you had to open an
editor, re-run something, or wait and try again. Run the second line a second time if you
want the honest number — the first `up` after `reset` pulls images.

**2. The cluster is really there, and `kubectl` is pointed at it.**

```sh
kubectl config current-context
kubectl get nodes
```
Passing looks like: the context is `kind-conductor`, and three nodes are `Ready` — one named
`conductor-control-plane`, two named `conductor-worker*`, all reporting `v1.35.5` in the
`VERSION` column. If the context says anything else, stop: every command after this went
somewhere you didn't intend.

**3. Ingress works end to end.**

```sh
kubectl -n ingress-nginx get pods -o wide
kubectl apply -f https://kind.sigs.k8s.io/examples/ingress/usage.yaml
curl http://localhost/foo
curl http://localhost/bar
```
Passing looks like: the controller pod is `Running`, and the `NODE` column says
`conductor-control-plane` — not a worker. Then `curl` returns `foo-app` and `bar-app`
respectively. That example is kind's own, verified present at
`https://kind.sigs.k8s.io/examples/ingress/usage.yaml` on 2026-08-11; its `Ingress` has no
`ingressClassName`, which is served because the vendored controller runs with
`--watch-ingress-without-class=true`.

If a path returns a **503** instead, the routing is fine and the backend isn't ready — check
`kubectl get endpoints foo-service bar-service` and `kubectl get pods -o wide`. Usually it is
the pod still pulling its image, since each node pulls independently. See
`docs/concepts/M0-ingress.md#traps-you-can-walk-into-here`.

Clean it up with `kubectl delete -f https://kind.sigs.k8s.io/examples/ingress/usage.yaml`.

**4. The registry is reachable from both sides.**

```sh
docker pull gcr.io/google-samples/hello-app:1.0
docker tag  gcr.io/google-samples/hello-app:1.0 localhost:5001/hello-app:1.0
docker push localhost:5001/hello-app:1.0
kubectl create deployment hello-server --image=localhost:5001/hello-app:1.0
kubectl get pods -w
```
Passing looks like: the pod reaches `Running`. If it sits in `ErrImagePull` or
`ImagePullBackOff`, the push worked from your host but the node cannot resolve the same name —
that is the `hosts.toml` step, explained in
`docs/concepts/M0-images-into-the-cluster.md#the-local-registry-and-why-the-alias-is-needed`.

Clean it up with `kubectl delete deployment hello-server`.

**And the part that isn't a command.** Open `kind/cluster.yaml` and
`k8s/ingress-nginx/README.md` and say out loud what each field is doing and what breaks
without it. M2's gate makes this explicit for every YAML file in the repo. M0 is where the
habit starts.
